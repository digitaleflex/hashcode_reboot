## Stack

- **Framework** : Next.js 16 (App Router) + `next-intl` v4
- **Locales** : `fr` (défaut, sans préfixe), `en` (sous `/en`)
- **Messages** : JSON plats dans `messages/{locale}.json` (namespaces hiérarchiques)
- **Proxy** : `next-intl/middleware` (réécriture locale) + garde d'auth dans le
  même fichier, `src/proxy.ts`

## Architecture

```
src/
├── i18n/
│   ├── routing.ts        # Config locales (localePrefix as-needed,
│   │                     # localeDetection false), helpers de navigation
│   └── request.ts        # Charge messages/{locale}.json via getRequestConfig
├── proxy.ts              # Guard auth + i18n (convention Next 16)
├── app/
│   ├── [locale]/
│   │   ├── layout.tsx    # Valide locale, setRequestLocale, NextIntlClientProvider,
│   │   │                 # et porte <html lang={locale}>
│   │   └── ...           # Toutes les routes sous [locale]
│   └── layout.tsx        # Root layout : charge globals.css seulement
messages/
├── fr.json               # source de vérité
└── en.json               # parité 100%, vérifiée par check:i18n
scripts/
├── check-messages.mjs    # Validation parité + placeholders ICU
└── analyze-i18n.mjs      # Analyse d'usage (namespace orphelins)
```

> Le layout racine est volontairement sans `<html>` ni `<body>` : c'est
> `app/[locale]/layout.tsx` qui porte l'attribut `lang`, seul moyen d'obtenir un
> `lang` correct sur `/en`.

## Routage

| URL | Comportement |
|-----|--------------|
| `/` | FR (défaut, `localePrefix: "as-needed"`) |
| `/en` | EN |
| `/fr` | Redirige vers `/` (canonical) |
| `/en/...` | Toutes routes préfixées |
| `/api/*` | **Pas de réécriture i18n** (les routes API sont hors de `[locale]`) |

## Utilisation dans le code

### Server Components
```tsx
import { getTranslations } from 'next-intl/server';

export default async function Page() {
  const t = await getTranslations('dashboard.home');
  return <h1>{t('welcomeCard.greeting', { firstName: 'Alex' })}</h1>;
}
```

### Client Components
```tsx
'use client';
import { useTranslations } from 'next-intl';

export function Component() {
  const t = useTranslations('auth.login');
  return <button>{t('submit')}</button>;
}
```

### Tableaux (raw)
```tsx
const items = t.raw('steps') as Array<{ n: string; title: string; desc: string }>;
items.map(item => <li key={item.n}>{item.title}</li>);
```

### Pluriels ICU
Dans JSON :
```json
"selectedCount": "{count, plural, =0 {aucun} one {# sélectionné} other {# sélectionnés}}"
```
Dans le code :
```tsx
t('selectedCount', { count: selected.length })
```


## Ajouter une nouvelle chaîne

1. **Ajouter dans `messages/fr.json`** (namespace approprié)
2. **Ajouter dans `messages/en.json`** (traduction)
3. **Utiliser `t('namespace.clé')`** dans le composant
4. **Vérifier** : `npm run check:i18n`

## Validation automatisée

```bash
npm run check:i18n
# Vérifie : clés manquantes/en trop, placeholders ICU cohérents
```

**Ne pas recopier le nombre de clés ici** : il bouge à chaque purge. Mesurer
avec `npm run check:i18n`, qui affiche le compte par locale et échoue si la
parité fr/en se rompt. `node scripts/analyze-i18n.mjs` complète l'analyse en
listant les namespaces référencés dans `src/` et les clés orphelines.

## Bonnes pratiques

1. **Namespaces** : Suivre la structure des routes (`landing.hero`, `dashboard.ateliers.session`, `admin.members.importInvitePanel`)
2. **Clés** : camelCase anglais (`primaryCta`, `errorMessage`, `tooltipAria`)
3. **Interpolar** : `{variable}` dans JSON, `t('key', { variable })` en code
4. **Ne pas traduire** : IDs techniques (`value`, `key`, `id`, emojis dans options), données d'exemple (CSV placeholder)
5. **ARIA** : Tous labels, descriptions, live regions passent par `t()`
6. **SEO** : `metaTitle`, `metaDescription`, `ogTitle`, `ogDescription` dans chaque namespace de page

## Middleware — Auth + i18n

Le fichier s'appelle `src/proxy.ts` (convention Next 16 ; Next 16 a renommé
`middleware` en `proxy`). Il exporte `proxy(req)` et délègue au middleware
`next-intl` :

```ts
// src/proxy.ts
import createMiddleware from 'next-intl/middleware';
import { routing } from './i18n/routing';

const intlMiddleware = createMiddleware(routing);

export function proxy(req: NextRequest) {
  // 1. Vérifie la session sur /account et /dashboard -> redirect /login
  // 2. Délègue à intlMiddleware (les routes /api/* ne le traversent pas)
  return intlMiddleware(req);
}
```

Deux points à connaître avant d'y toucher :
- `localeDetection: false` est positionné dans `src/i18n/routing.ts` : la locale
  vient de l'URL uniquement, sinon un navigateur anglophone voit `/` basculer
  en `/en` et casse `metadata.alternates.canonical`.
- Le nom du cookie de session est recopié en dur dans ce fichier : il s'exécute
  en Edge et ne doit pas tirer de module serveur.

## Déploiement

- `next.config.ts` wrappe avec `createNextIntlPlugin("./src/i18n/request.ts")`
- Pas de config supplémentaire Vercel/Netlify (détecté automatiquement)
- `localePrefix: "as-needed"` → FR sans préfixe = SEO optimal pour marché primaire
- La CI valide les clés à chaque push : `node scripts/check-messages.mjs`
  (étape « Validate translation keys » de `.github/workflows/ci.yml`).

## Dépannage

| Problème | Solution |
|----------|----------|
| `useTranslations` non défini | Vérifier `"use client"` en haut du fichier |
| Clé introuvable | `npm run check:i18n` |
| Placeholder manquant | Même script, compare fr/en |
| Hydration mismatch | Namespace cohérent server/client, pas de `Date.now()` dans messages |
| API routes 404 | Les routes API sont hors de `app/[locale]/` : aucune réécriture i18n ne les touche |
| Page accessible en `/fr/...` sans redirection | `localePrefix: "as-needed"` : `/fr` doit rediriger vers `/`, voir `src/i18n/routing.ts` |
